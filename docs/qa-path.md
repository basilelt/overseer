# QA path

The walk a QA agent takes through the app before a PR is marked ready. It uses the app the way a person does: the production frontend, a real daemon, real agent processes and terminals, every control clicked. It complements the tests; it does not replace them (see "QA like a human, with real agents" in `AGENTS.md`).

- **Feature PR**: run [Setup](#setup), the smoke steps **A1–A3**, every area the PR touches, and **M** (life events).
- **Branch that merges several others, or before a release**: run the whole path.
- **Bugs found on the way are fixed immediately**: in this PR when they belong to the change, otherwise at once in their own fix PR, even when they predate the branch. A QA run never ends with a list of "follow-ups".
- **Report**: the PR lists the step IDs you ran, what failed and was fixed (with the test that now covers it, or the PR that fixed it), and the steps you could not run, with the reason.

## Setup

The sandbox never touches the user's own daemon, state or sessions.

```sh
scripts/qa/sandbox.sh build    # daemon (cargo, -j 2) and production frontend (not VITE_MOCK) into $QA_DIR/dist
scripts/qa/sandbox.sh start    # sandboxed daemon, loopback proxy to its socket, static server for the app
scripts/qa/sandbox.sh crash    # kill -9 the daemon (life events)
scripts/qa/sandbox.sh stop     # stop everything; `clean` also deletes $QA_DIR
```

- **macOS**: `build`, `start`, `crash`, `stop` and every browser mode work (Chromium, WebKit). The script uses `python3` where `setsid` is missing, honours `CARGO_TARGET_DIR` for the daemon binary, and adds `/opt/homebrew/bin` and `/usr/local/bin` to the daemon's `PATH`; `drive.py` also searches `~/Library/Caches/ms-playwright`. `desktop-build`, `desktop` and `shot` need Xvfb and WebKitGTK: they are Linux-only and exit with a message on macOS, so steps marked **(desktop)** are reported as not run there (run the real app by hand instead).
- `QA_DIR` defaults to `/tmp/sbqa`. Keep it short: a unix socket path must stay under about 100 bytes.
- The daemon runs with its own `HOME`, state dir, runtime dir, Claude and Codex config, `GIT_CONFIG_GLOBAL=/dev/null`, and `tests/stubs` first on `PATH`. Sessions therefore start real processes from the stub CLIs: they print a `❯` prompt, echo what you type (`got: …`), and log their command line to `$QA_DIR/stub.log`. Typing `done` ends a turn, `task` / `untask` send `TaskCreated` / `TaskCompleted`, so a task moves to Review. The `codex` stub behaves like Codex 0.165+: it creates its thread (a rollout under `$QA_DIR/home/.codex/sessions`) on the first `busy`, not at launch, reports its hooks with a pid that is not its own (real Codex runs hooks from a shared `codex app-server`), Ctrl+C makes it quit cleanly like Codex, and `tool` runs for 8 s a process with the argv of Codex's Linux sandbox (`bwrap … -- …/bin/codex --sandbox-policy-cwd …`).
- A sample git repository is created at `$QA_DIR/home/proj`. Add files there as a step needs them.
- The daemon's `SHELL` is `/bin/sh`; set `QA_SHELL` (for example `QA_SHELL=/bin/bash`, `/bin/zsh`, `/usr/bin/fish`) on `start` to run shells and post-agent shells as a user of that shell would.
- Drive the app with Playwright and `scripts/qa/drive.py`: `launch(p, mode=...)` opens a browser with `scripts/qa/shim.js`, which replaces the Tauri IPC with calls to the proxy (requests, `/v1/events` SSE, terminal websockets, ports). Like the desktop app, it checks `/v1/version` every 5 s and reports `reconnecting` while the daemon is down, holding requests until it answers again. `open_app(pg, "?theme=light")` loads it and dismisses the welcome tour. Set `QA_CHROME` to use a specific Chromium binary; without it, `drive.py` falls back to the newest Chromium or headless shell installed by Playwright when the default build is missing. The shim answers `browsers_list` (one **QA Browser**), `local_network_status` (`notApplicable`), `plugin:clipboard-manager|write_text` (`window.__qaClip`), and records `open_external` and `browser_open_with` calls in `window.__qaOpened` (`{via, url}`) instead of leaving the page.
- **Modes**: QA runs in every mode a user can be in. `mode` (or `QA_MODE`) picks one:
  - `web`: Chromium at 1440×900, the desktop layout in a browser.
  - `android`: Chromium emulating a Pixel 7 with touch (the Android app's WebView is Chromium); phone layout.
  - `android-tablet`: Chromium emulating a Galaxy Tab S9 portrait (640 px), phone layout; `android-tablet-landscape` (1024 px) is the desktop layout with touch, right at the switch point.
  - `iphone`: WebKit emulating an iPhone 15 with touch (the iOS app is WKWebView); phone layout.
  - `ipad`: WebKit, iPad Pro 11 portrait (834 px); the phone layout, since the app uses it on mobile below 1024 px.
  - `ipad-landscape`: WebKit, iPad Pro 11 landscape (1194 px); the desktop layout with touch.
  - `desktop`: the real Tauri app, below.
  The WebKit modes load the app from the proxy port (`QA_PORT`), which also serves `$QA_DIR/dist`, so the API is same-origin. WebKit has no switch to turn CORS off. The first run needs `python3 -m playwright install webkit` (and `install-deps webkit` as root).
- **Layout check in every mode**: `PYTHONPATH=scripts/qa python3 scripts/qa/overflow.py [modes…]` opens Agents and Tasks in each mode, saves `$QA_DIR/overflow-<mode>-<view>.png`, and fails when a button, input or link sits outside the screen (rows that scroll sideways are allowed). Look at the screenshots as well.
- Read the API directly when a step needs proof: `curl http://127.0.0.1:47811/v1/terms`, `/v1/tasks`, `/v1/lines?all=true`, `/v1/ports`.
- A pending server update (More → restart row, the update banner) is presented with `?qaserver=<running>:<installed>:<terminals>` on the app URL (for example `?qaserver=0.34.0:0.35.0:2`); the shim records the restart in `window.__qaLog` as `conn_restart_server`.
- **Chat with real content**: start a stub session with `POST /v1/terms {"cwd": "<proj>", "cmd": ["claude", "--session-id", "<uuid>"]}`. Then write its transcript to `$QA_DIR/home/.claude/projects/<cwd with every non-alphanumeric char replaced by ->/<uuid>.jsonl`, one JSON object per line (`type` user or assistant, `message.content` with text, `image`, `tool_use` or `tool_result` blocks). Only append to it: the reader follows appended lines and ignores in-place edits.
- **The desktop app (WebKit)**: headless Chromium is not the engine users run. The desktop app renders with WebKitGTK on Linux and WKWebView on macOS, and they differ on CSS (`user-select` only works as `-webkit-user-select`), text selection, drag gestures and the clipboard. After `start`, run `scripts/qa/sandbox.sh desktop-build` once (debug Tauri build, `-j 2`; into `$CARGO_TARGET_DIR` when set, which `desktop` also launches from), then `desktop`: it starts Xvfb on display `$QA_DISPLAY` (a number such as `97` or `:97`, default 93, Mesa EGL so the NVIDIA driver does not crash it), the Vite dev server on port 1420 and the real app, with its own `HOME` and connected to the sandboxed daemon. Drive it as a person with `xdotool` (`DISPLAY=:93 xdotool mousemove X Y mousedown 1 …`, `type`, `key`), take screenshots with `sandbox.sh shot <name>` (written to `$QA_DIR/<name>.png`), and read the clipboard with `DISPLAY=:93 xclip -o -selection clipboard`. Coordinates are screen pixels of the 1440×900 display. `desktop-stop` stops the app; `stop` stops it too. It needs `Xvfb`, `xdotool`, `xclip`, ImageMagick and the WebKitGTK 4.1 development libraries. Steps marked **(desktop)** must be run there; the others run in each mode they apply to (`web` and `desktop` for desktop-layout steps, `android`, `android-tablet`, `iphone` and `ipad` for **L**, `android-tablet-landscape` and `ipad-landscape` for touch on the desktop layout).
- **Gotchas**: `window.__qaLog` lists the Tauri commands the shim does not handle. One that is not in the shim's `NULL_COMMANDS` list rejects with `unknown Tauri command`; a feature that depends on a command needs it handled in `shim.js` or added to that list, and `scripts/qa/qa.test.sh` fails until every command in `app/src/lib/daemon/tauri-commands.ts` is one or the other. Never `pkill -f $QA_DIR`, because it matches your own shell; `sandbox.sh stop` kills by pid. Delete copied transcripts afterwards if they came from real sessions.

## The path

Each step is **Do → Expect**. Check every screenshot for overlaps, clipped text and unreadable contrast, and keep the browser console free of errors.

### A. Start and connect

- **A1** Open the app → the title bar shows **Local** with a green dot and the CPU/RAM chip. The welcome card offers **Skip** and **Take the tour**.
- **A2** **Take the tour**, step through it, close it → every step points at a visible control. Reload: the tour does not come back.
- **A3** Reload the app, then stop and start the daemon (`sandbox.sh stop`, then `start`) → the app reconnects on its own, without an error left on screen.
- **A3b** Open two session tabs and a split, palette **Disconnect**, then **Reconnect** (or connect to the same host again) → the same tabs, the same split and the same selected tab are back, as after a relaunch, and the terminal accepts typing. With two hosts in the window, disconnecting one leaves the others' tabs alone, and reconnecting it restores only its own.
- **A4** Host chip → **Connect to host…**, type `box`, Enter (default **One window per host**) → the window now shows **box** alone, with no extra connection (`window.__qaLog` has one `conn_connect` per connect, no slot). Session rows in the sidebar show no host name.
- **A5** Palette → **Add a host to this window…**, type `gpu`, Enter → the sidebar shows a **box** and a **gpu** section (name, address or state, count, **…**; Local reads "This computer"), the host chip reads "2 hosts", **gpu** is in the main area and **box** stays connected (`conn_connect h1 …` in `window.__qaLog`). Click the **box** header or one of its sessions → **box** comes into the main area at once, with its tabs back, and no new `conn_connect`. Open a shell: its tab carries a **box** tag; turn off Settings → Connection → **Show the host on tabs** → the tag goes.
- **A6** **…** on a host section → **Show in the main area**, **Collapse <host>** (the section folds to its header and stays folded after a reload), **Move to its own window** (a window opens on that host: `window.__qaWindows`, and the section leaves this window), **Disconnect, sessions keep running** (the section goes, `conn_disconnect <slot>`). Disconnect the host in the main area from the host chip → another host of the window takes its place, still connected. **(desktop)** Add `nohost.invalid` → the dialog fails at **Connecting** with ssh's message, its section shows a red dot and the other hosts keep their sessions; palette **Add a host to this window…** is still offered; click another host → the failed one, never connected, leaves the window.
- **A7** Settings → Connection: **Windows and hosts** shows **One window, all hosts** and **One window per host**; pick the first, connect to a host from the host chip → it is added, not replaced. Turn on **Ask each time I connect to a host**, connect to `stage` → "Where should stage open?" with **Back**, **Add to this window**, **Open in a new window** (the mode's choice first and focused) and **Remember for stage**; tick it and **Open in a new window** → a window opens for stage, and the next connect to stage does the same without asking. **Forget remembered choices (1)** clears it.
- **A8** With two hosts in the window, reload → both sections come back (the main window reconnects them); turn off **Reconnect every host at launch**, reload → only the host of the main area comes back. A session waiting for input on the background host raises a notification titled "<host>: …"; opening it from the bell brings that host into the main area and selects the session. Repeat A5–A7 in light and dark, and check a phone viewport still shows one host. With a second sandbox daemon as the extra host (start it with its own `QA_DIR`, `QA_PORT`, `QA_WEB`, and the first with `QA_SLOT_PORT` set to its port), open a session on each host, disconnect one from its **…** menu → the other host's tabs and terminal history are untouched and still accept typing; add the host again → its tabs come back.

### B. Projects and tasks (Kanban)

- **B1** Tasks → **Create Project** → type the repo path → Enter → the project appears in the project filter.
- **B2** **Add Task**: title, description, attachments (paste or **browse**; in the browser the shim keeps the bytes and uploads them to the daemon like the desktop app, and the file lands in `$QA_DIR/home/.overseer/tasks/<id>/` and in the agent prompt after **Start**), project, agent, model, depends on, type, profile, effort → **Create task** → a card appears in Pending with the right project, agent and effort.
- **B2b** Profiles by task type: **Agents & models → By task type**, map **Migration / refactor** to **Max** and **Search / triage** to **CLI defaults**. **Add Task** → choose Type **Migration / refactor** with Profile left on Default → the Profile option reads `Default (Max)` and the model and effort switch to Max's; change the type back to **Not set** → they return to the workspace or default profile. Create it, **Start** → `stub.log` shows `--model opus --effort max` and the tab chip reads Max. **Import** a GitHub issue labelled `bug` (or a Jira Bug) → Type becomes **Bug fix**. Duplicate a profile and **Save profiles**, map **Bug fix** to the copy, then delete the copy and **Save profiles** again → the Bug fix rule goes back to **Workspace or default**. To exercise the import with the `gh` stub, export `SB_GH_DIR` before `sandbox.sh start` (it is passed to the daemon), add a GitHub source in **From issue…** and write the issue list JSON (with `labels`) to `$SB_GH_DIR/_.json`.
- **B3** Drag the card to **In progress** → a `task/<n>-<slug>` worktree is created and the agent starts there (`stub.log` shows `--session-id`). The card shows progress.
- **B3a** `sandbox.sh stop`, then `SB_STUB_DROP_ENTER=1 sandbox.sh start` (the stub Claude shows the first prompt in its box without sending it) → create an **Auto** task → its terminal shows the prompt sent once (`got: <title> …`) within a few seconds. Restart without the variable and start another task → it gets exactly one `got:` line and no extra Enter.
- **B4** Open a card → the detail modal shows the Urgent and Important toggles, Depends on and Messages. Send a message → it shows "delivered when it starts", or reaches the running agent.
- **B4a** Agent messaging: create task A and B in the sandbox repository and C in a second repository, then from the sandbox environment `POST /v1/tasks/<B>/messages {"body": "hi", "from": "<A>"}` → 201 and B's Messages shows it from #A; to C → 403 "belongs to another project". Settings, Defaults, **Agents message each other** is on; turn it off → A to B is refused with "turned off", a message you send from B's detail still arrives, and a quorum subtask's orchestrator still reaches it. Reload → still off. Search `message` → the row shows. After an update from 0.35, **What's new** shows **Agents stay in their project**, pointing at the switch (or the Settings button when Settings is closed).
- **B4b** Side tasks: Settings, Defaults, **Agents file what they find as tasks** is on; from the sandbox environment run `overseer mcp` with `initialize` and `tools/list` → the instructions say to `create_task` what you find, and `create_task` has no restriction. Turn the switch off → a new `overseer mcp` says to fix it yourself in your own task, and `create_task` says to create one only when asked; `create_task` from a task agent still creates the task. Reload → still off. Search `find` → the row shows. After an update from 0.35, **What's new** shows **Autonomous agents**, pointing at the switch (or the Settings button when Settings is closed).
- **B5** **Matrix**, search, the project filter, **Hide session tasks** → the board filters as labelled. **Organize** proposes, and never moves anything without confirmation.
- **B6** A task that depends on another stays in Auto until the other one is done.
- **B6a** The board shows the columns Pending, Auto, In progress, Review, Merged and Closed, in that order; Merged and Closed start collapsed. Drag a Review card to **Merged**, then to **Closed** → it stays where dropped after a reload. A task whose branch is merged into the default branch (`git -C <repo> merge --no-ff task/<n>-…` in the sandbox repository) moves from Review to **Merged** on its own within a minute; a Closed task with its worktree still on disk does too. A task that depends on a Merged task is no longer blocked.
- **B6b** Agent moves through MCP: run `OVERSEER_TASK_ID=<id> overseer mcp` with the sandbox environment and send `initialize`, then `tools/call` `set_task_status` with `{"status": "merged"}` while the task branch is not merged yet → refused with "branch task/<n>-… is not merged into main yet: merge it first, then set merged" and the card does not move; merge the branch (`git -C <repo> merge --no-ff task/<n>-…` in the sandbox repository) and send it again → the card moves to Merged; `{"status": "in_progress"}` while its agent runs → the card goes back to In progress and returns to Review after the next `done`; `{"status": "pending"}` → refused with an error and the card does not move.
- **B7** **(desktop)** With 30+ cards in two columns (Closed expanded), drag a card across the board and back → the ghost follows the cursor without stutter, the drop line moves card by card, and no text on the board gets highlighted. `PYTHONPATH=scripts/qa python3 scripts/qa/kanban_drag.py` repeats it under 4× CPU throttling and fails when one drag forces more than one layout per ten pointer moves (`DRAG_MOVES`, `DRAG_LAYOUT_BUDGET`). On the mock build, add `&scale=200` to the query for a heavy board.

- **B8** **Add Task** with the agent **Claude Code** → a **Quorum** switch shows; choose **Gemini CLI** as the agent → the switch is disabled with "Only Claude Code and Codex can run a quorum." Back on Claude Code, switch it on → **Workers** and **Reviewers (1 or 2)** chips show the installed agents; a third reviewer cannot be selected and the last worker or reviewer cannot be unselected. **Create task** → the card in Pending has a **Quorum** chip, and its detail lists the workers and reviewers. Reload → the chip is still there.
- **B8a** Start the quorum task (the stub orchestrator creates subtasks for different agents with `create_task`, or create them with `POST /v1/tasks`) → subtasks start by themselves with the worker agents (`stub.log`). When a worker reaches Review, one reviewer task per reviewer appears with a **Reviewer #N** chip and starts by itself.
- **B8b** Vote from the reviewer terminals: `overseer vote approve "ok"` in one, `overseer vote reject "no tests"` in the other (sandbox environment), then the orchestrator's vote → the worker card shows **2/3 accepted · Round 1** or **1/3 rejected · Round 1**, and the task detail lists each vote with its reason. With one reviewer, one rejection rejects. A second vote by the same voter is refused; a vote from a task that is not a reviewer of that worker is refused.
- **B8c** After a rejection, the orchestrator gets a `Quorum:` message with each vote's reason and forwards the fixes to the worker; a worker whose terminal still runs goes back to **In progress** at once, and when its next turn ends (`busy` then `done` in a Claude stub worker) the tally restarts at **Round 2** with new reviewer tasks. After an acceptance, the orchestrator gets the branch to merge into its own; the worker card keeps its tally and moves to Merged once the orchestrator's branch lands in the default branch.
- **B8d** `sandbox.sh crash`, then `start`, with a quorum task mid-vote → the quorum chip, the reviewer tasks and the votes already cast are all still there, and the pending votes can still be cast.

### C. Agent sessions

- **C1** Agents → open the task's session → the terminal shows the agent prompt. Typing reaches the agent (`got: …`).
- **C2** Type `done` → within a few seconds the task moves to **Review** and the session goes idle.
- **C3** Chat header (session bar): Pause and Close. Side panel: Pin, Last message, Work log, Todos, Changes, **Open review** → each acts and updates. A paused session shows **Resume** in the chat header, and resuming relaunches the agent with `--resume <same session>`.
- **C4** Start a session in a folder that is not a git repository (for example the agent started by the feedback sheet) and let it run a few tool calls, then select it without reloading → the side panel shows its activity (**LAST MESSAGE**, **WORK LOG**, and **TODOS** / **EDITED FILES** when the agent made any), not "No activity yet", and **CHANGES** with "Not a git repository, so there are no changes to show" and no **Open review** button. The browser console has no errors and the network log has no 4xx. Select a session in a git repository → **CHANGES** and **Open review** are back.
- **C5** Pause a session, then click **Resume** in the chat header (not in the terminal) → the session is active again, the button shows **Pause**, and `stub.log` shows `--resume <same session>`. The held terminal's "press Enter to resume" prompt is answered by the click.
- **C6** Pause and resume the same session three times in a row (chat header **Pause**, then **Resume**) → the state flips each time, the terminal shows "press Enter to resume" while held and the agent prompt after, and `stub.log` has one `--resume <same session>` per cycle. Repeat with `sandbox.sh crash` and `start` while held and while active: the state survives.
- **C6a** Agent asking first: stop a session (kill its term), then `touch $QA_DIR/stub.log.trust` so the `claude` stub stops at a folder trust prompt (Enter answers "No, exit", typing `trust` accepts), and press **Resume** (chat header, or **Resume in terminal** in the pane) → the header reads **Starting**, Resume is disabled ("The agent is starting in its terminal"), and the chat shows a note with **Open terminal**; pressing Resume again or reloading starts no second agent (`stub.log` has one `--resume`). **Open terminal** shows the prompt; type `trust` → the session comes back Open. Repeat from a paused session (Enter on the held stub, then the prompt): a second Resume does not answer the prompt. Close a session still at the prompt → its term ends. Run in `web`, `android` and `iphone`; remove the file afterwards.
- **C6b** Pause a busy session in the chat header → the state reads "Running" with a muted "· Pause after this turn" next to it, and **Cancel pause** (tooltip "Cancel the queued pause") appears; click it → the pause is dropped ("Pause cancelled"). Pause again and let the turn end → the pending pause applies and the session shows Paused. Queue a pause on a busy session, then `sandbox.sh crash` and `start` → the pause is not lost: once the agent is restored it applies and the session shows Paused (right away when the turn already ended). Click **Close** and wait 3 seconds → it goes back to **Close**; click **Close**, then switch to another session within 3 seconds and click **Close** there → it asks **Close?** again instead of closing. Right-click a single session in the sidebar > **Pause after this turn** (or **Cancel the queued pause** while one is queued) → same result and toast as the chat header, and no bulk dialog; a paused session offers **Resume** there, which resumes it like the header button and brings the header back to Open (the stub log shows one `--resume`); with two sessions selected, the menu offers **Hold** and opens the bulk dialog.
- **C6c** Select an idle Codex session and choose **Close agents in selected** → the dim gray `›` composer passes the empty-input check and **Close** shuts down the session. Type into the composer and repeat → the check blocks closing while text is present.

- **C7** Codex, several sessions in one repository: start two Codex sessions in `proj` and one in another repository (`POST /v1/terms {"cwd": …, "agent": "codex"}`), and leave an older Codex session of `proj` held → opening them wakes no held session. Type `busy` in each, one after the other → each gets its own session line with its own pid, and the held one stays held.
- **C8** In one Codex session type `tool`, then `done` → for the 8 s of the tool no other session of the repository turns active, appears or disappears; only the busy dot of the session that ran it changes.
- **C9** Type `busy` again in the oldest Codex session, so it is the most recent one → no pid moves between session lines (`/v1/lines?all=true`). Open a fourth Codex session in `proj` and type `busy` → only its new line appears. Type `exit` in the first one → only its own line is held.
- **C10** In a Codex session press Ctrl+C (or type `exit`) → the tab stays open and shows `codex exited. Session <id>, resume with: … codex resume <id>`, then a shell prompt in the same folder that runs commands. Press Ctrl+W on that tab → the shell is a live session, so the "End this session?" dialog shows (as in E3); **End session** closes the tab and the shell. Close a tab whose Codex is still running (**End session**) → it closes without a shell left behind.
- **C11** Real CLIs: the stubs never fail the way a real CLI does. On a release, or when a change touches agent launch or resume, start a daemon like the sandbox's but with the real CLIs first on `PATH` (still its own `HOME` and state dir), and start each installed agent from **+** (Claude Code, Codex, Gemini CLI, Antigravity, Copilot CLI, opencode, Amp, Cursor Agent, Mistral Vibe) → each keeps running in its tab (a login screen is fine), gets one session line on that tab (Mistral Vibe only once the first message is sent, since it writes no session before it), and Ctrl+C leaves the shell with its session and resume command. An agent folded under **Not installed (N)** at the bottom of the **+** menu and greyed out there has no install command (Antigravity) or its `--version` fails; one marked **Install** is not installed: install it from there (**C13**) and check it again.
- **C12** In a running Claude session click **Close** in the chat header (it turns into **Close?**; click again to confirm) → the tab stays open (in both Workspaces and By status) and shows `claude closed. Session <id>, resume with: …`, then a shell prompt that runs commands; the session shows hung-up. Start `claude` by hand from a shell tab and close it the same way → the shell stays, no new note. For a session owned by a task, closing ends its terminal and drops its tab with no shell afterwards.
- **C13** Install an agent: the sandbox has no Amp or Cursor Agent (its stubs cover opencode, so that one counts as installed), so the title bar **+** and the tab bar **+** fold them under **Not installed (2)** (unfold it) where they show **Install**, as do the agent picker (Settings, Agents and the task dialog) and the palette (**Install Amp**). Hover Amp in the unfolded title bar **+** → the tooltip names the command. Click it → a shell tab "Install Amp" opens, shows `$ npm install -g …` and the stub's `added 1 package`, then closes on its own; the toast says "Amp is installed" only when a real `amp` landed on `PATH` (the stub installs nothing, so it says "Amp installed, but the daemon does not find it on its PATH"), and `stub.log` has `npm install -g --allow-scripts=@ampcode/cli @sourcegraph/amp`. Restart the sandbox with `SB_NPM_FAIL=1 scripts/qa/sandbox.sh start` (its `npm` stub then fails) and install Amp again → the tab stays open with `npm ERR! stub failure` and `Install failed with exit code 1`, and the "did not install" error toast. Antigravity, when missing, stays greyed out with its download hint. Do not install Cursor Agent in the sandbox unless you mean to: `curl` is not stubbed, so its real installer downloads ~500 MB into the sandbox `HOME`, exits 0, and the toast says the daemon does not find it on its `PATH` (its `~/.local/bin` is not on it). On the phone (**L1**) tap **+** → the palette lists **Install Amp** and it opens the same terminal.
- **C14** Mistral Vibe: Settings → Agents → **Agent hooks** → switch on **Mistral Vibe** → `~/.vibe/hooks.toml` lists `session_start`, `pre_agent` and `post_agent` (each with `match = "main"`), `post_tool`, `notification` and `session_end`, each calling `overseer hook vibe …`. Start **Mistral Vibe** from **+** → `stub.log` shows `vibe --auto-approve`. **Add Task** on Mistral Vibe and start it → `stub.log` shows `vibe --trust --auto-approve -- <title…>`. ### D. Review

## Keeping the path current

The path describes the app as it ships, so it changes with the app. A PR that changes what the user can do updates this file in the same PR.

- **New feature**: add **Do → Expect** steps in the area where a user meets it, or a new lettered section for a new area. Cover the happy path, the error the user can hit, and, when the feature keeps state, what happens across a reload and a daemon crash (add to **M**).
- **Changed behaviour**: rewrite the steps that pin the old behaviour. Never leave a step that describes something the app no longer does.
- **Removed feature**: delete its steps in the PR that removes it.
- **IDs**: append new numbers within a section, never renumber existing steps (PR reports refer to them), and do not reuse the number of a deleted step.
- **Harness**: if the feature calls a Tauri command the shim does not handle (`window.__qaLog`), extend `scripts/qa/shim.js` in the same PR. Keep `scripts/qa/sandbox.sh` in step with new environment variables the daemon reads.
- **Write what a person does and sees**, not how the code does it. Name the visible labels exactly as the English UI shows them, and update them when the strings change.
