Architecture Overseer

Trois moteurs aux rôles distincts. Overseer sauvegarde les sessions Claude et Codex et se souvient d'où tourne chaque worktree. Yard fait tourner le code à tester, un environnement par PR. feedback-hub transforme un retour utilisateur en ticket qualifié. TwinFactory regarde le tout sans rien piloter.

Vue d'ensemble

hébergé commun exécution Overseer : -api (hébergé), -daemon (un par station), -app (poste du dev) externe flux secondaire ou attache SSH

Overseer ne crée aucun environnement : c'est le rôle de Yard. Overseer référence seulement l'env d'une PR. Un env vit aussi longtemps que la PR, une ligne aussi longtemps que le travail d'une personne. Ce sont deux cycles de vie différents, donc deux moteurs.

Overseer : sauvegarder les sessions, se souvenir des worktrees

Le cœur de Overseer tient en deux missions. Tout le reste (relais de commandes, envs, vues avancées) vient après.

  1. Sauvegarder chaque session Claude et Codex : l'agent, l'identifiant de session pour la reprendre, le ticket, les dates de début et de dernière activité. Une session survit à un redémarrage ou à une machine saturée.
  2. Se souvenir d'où tourne chaque worktree : la station (Mac, VM SSH ou pod), le chemin, le dépôt et la branche. Retrouver une session, c'est savoir où aller la reprendre.

Trois briques : overseer-daemon, overseer-api, overseer-app

Par personne

  • Chaque ligne a un propriétaire : un humain, ou un compte agent comme feedback-bot.
  • Le Board d'un dev montre ses lignes, toutes stations confondues : Mac, VM SSH, runner.
  • TwinFactory voit toutes les lignes de tout le monde, en lecture.

Par ticket

  • Un ticket porte plusieurs lignes : l'agent du hub, puis le dev, puis un reviewer.
  • La vue ticket regroupe ses lignes, ses PR et ses envs.
  • Une ligne sans ticket reste permise (exploration) ; on la rattache plus tard.
// le contrat central, partagé par tous les clients
interface Line {
  id: string;
  owner: string;                     // personne ou compte agent
  ticketKey?: string;                // AS-1234
  stationId: string;                 // mac-bob, vm-node2-dev1, runner-3
  agent: 'claude' | 'codex';
  agentSessionId: string;            // claude --resume / codex resume
  repo: string;
  branch: string;
  worktreePath: string;
  prUrl?: string;
  envRef?: string;                   // id côté Yard, jamais une copie de son état
  origin: 'dev' | 'feedback';
  state: 'active' | 'idle' | 'held' | 'hung-up';
  lastActivityAt: string;
}

Parcours type : d'un feedback au merge

  1. feedback-hubUn utilisateur signale un problème dans l'app. Le hub capture les preuves et cherche un fix existant.
  2. feedback-hub → OverseerLe hub demande une ligne pour feedback-bot sur un runner. Overseer la branche. L'agent crée le ticket AS-… par le MCP Jira, puis corrige sur feedback/AS-….
  3. runnerL'agent pousse et ouvre la PR draft avec le label preview.
  4. YardIl voit la PR, crée le namespace, déploie, publie env.ready avec l'URL. Le hub et Overseer l'affichent.
  5. feedback-hubLe rapporteur teste sur l'URL et répond ✅ ou ❌. Une réponse relance la même ligne, donc la même session agent.
  6. Mac du devLe dev reprend : overseer patch AS-…. Soit il s'attache en SSH à la ligne du runner (même session), soit il ouvre sa propre ligne locale sur la même branche, avec un résumé de la conversation de l'agent.
  7. GitHubMerge. Yard détruit l'env, Overseer raccroche les lignes, TwinFactory se met à jour.

Une session Claude ou Codex vit dans les fichiers de la station où elle a tourné. La reprendre « telle quelle » impose d'être sur cette station, d'où l'attache SSH. Sinon on la remplace par une nouvelle ligne qui hérite du contexte.

Cahier des charges par outil

Pour chaque outil : sa mission, ce qu'il doit faire, ce qu'il ne fait pas, et le test qui dit que la première version est livrée.

overseer-daemon

chaque station

Sur chaque machine, sauvegarder les sessions Claude et Codex et savoir où tourne chaque worktree.

Doit

  • Découvrir les sessions existantes dans les fichiers de Claude Code et de Codex : identifiant, dossier de travail, dates.
  • Découvrir les worktrees git des dépôts suivis : chemin, dépôt, branche.
  • Rattacher une session à un ticket : déduit du nom de branche (AS-1234) ou fixé à la main.
  • Suivre l'état (active, idle) grâce aux hooks de Claude Code.
  • Garder un registre local qui fonctionne sans réseau, puis le synchroniser vers overseer-api par une connexion sortante.
  • Exécuter les commandes : reprendre, mettre en attente (arrêter le process en gardant l'identifiant), fermer.

Ne fait pas

  • Créer des environnements, écrire dans Jira ou GitHub.

Livré quand : après un redémarrage du Mac, chaque session récente est listée avec son worktree, son ticket et sa commande de reprise, et la reprise fonctionne.

overseer-api

hébergé

Le registre commun de toutes les stations, que les autres outils interrogent.

Doit

  • Enrôler une station avec un jeton qui lui est propre.
  • Recevoir les inventaires et les battements de cœur des démons.
  • Répondre aux lectures : lignes par personne, par ticket, par station.
  • Publier les changements d'état des lignes à TwinFactory et feedback-hub.
  • Relayer une commande vers la bonne station, et garder la trace de qui l'a demandée.

Ne fait pas

  • Exécuter du code ou lancer un agent.
  • Stocker le contenu des conversations : seulement leurs métadonnées.

Livré quand : les lignes de deux stations différentes (le Mac et une VM) apparaissent dans une même lecture.

overseer-app

poste du dev

L'interface du dev pour retrouver, reprendre et ranger son travail.

Doit

  • V1, en ligne de commande : overseer ls, resume, hold, close, link <ticket>.
  • Reprendre une session distante par SSH sans que le dev ait à savoir où elle tourne.
  • Montrer combien de sessions sont actives, pour éviter de saturer la RAM.
  • V2, en plugin cmux : un Board par ticket, l'accès au diff, au commit et au stash du worktree.

Ne fait pas

  • Garder son propre état : tout vient du démon local.

Livré quand : overseer ls puis overseer resume rouvrent une session de la veille, en local comme sur une VM.

Yard

hébergé · kube

Un environnement éphémère par PR sur Kubernetes, sans que personne n'ait à le demander à la main.

Doit

  • Se déclencher sur le label preview d'une PR.
  • Créer un namespace, y déployer les services de la PR et une copie de base.
  • Publier l'état et l'URL de l'env.
  • Appliquer un TTL et un plafond, et tout supprimer au merge ou à la fermeture de la PR.
  • Refuser les images Docker sous le seuil d'efficience des couches (décision de la réunion du 28/10).

Ne fait pas

  • Connaître les sessions, les personnes ou les tickets.

Livré quand : poser le label donne une URL qui fonctionne, et fermer la PR supprime le namespace.

feedback-hub

hébergé

La pré-qualification : un retour utilisateur devient un ticket documenté, un fix en draft et une preview à valider.

Doit (il garde)

  • Le widget, le picker, le masquage, les captures et le replay vidéo.
  • Les appels backend des 30 dernières secondes.
  • Le dédoublonnage et la recherche de fix existants.
  • Le triage, Slack, la page de thread. Jira passe par son agent et le MCP Jira.
  • Les règles de qualification : checks des dépôts, retries, verdicts.

Délègue

  • Les previews à Yard, par le label de PR.
  • Les worktrees et les sessions de l'agent à Overseer, par une ligne feedback-bot.
  • Pour migrer sans casse : un port Workspace et un port Previews, chacun avec un adaptateur embedded (le code actuel, en local) et un adaptateur remote.

Livré quand : un feedback aboutit à un ticket, une PR draft et une preview Yard, sans aucun worktree ni port local côté hub.

TwinFactory

hébergé

L'inventaire visuel de l'usine. Elle montre, elle ne pilote pas, et elle n'est pas le poste de travail des devs (décision de la réunion du 28/10).

Doit

  • Lire quatre sources en direct : Jira, GitHub, overseer-api, Yard.
  • Vue ticket : ses lignes, ses PR, sa CI, son env.
  • Vue stations : chaque agent, où il tourne, actif, idle ou en attente.
  • Offrir un lien « reprendre » qui ouvre la session dans overseer-app.

Ne fait pas

  • Écrire où que ce soit, ou envoyer une commande.

Livré quand : un ticket affiche ensemble sa PR, son env Yard et les sessions qui y travaillent.

À trancher

1. Comment on demande un env

  1. Label sur la PR, lu par Yard (recommandé). Couplage le plus faible : personne n'appelle Yard.
  2. API de Yard, appelée par le hub ou Overseer. Utile pour un env sans PR.
  3. Les deux : label par défaut, API pour les cas particuliers.

2. Quand le dev reprend la ligne d'un agent

  1. Attache SSH par défaut, nouvelle ligne locale au choix (recommandé).
  2. Toujours une nouvelle ligne locale, avec résumé.
  3. Toujours l'attache SSH.

3. Sur quoi construire Yard

  1. L'outil qu'Alice installe pour Kubernetes, enrichi d'un statut publié (recommandé).
  2. Un opérateur maison avec une ressource PreviewEnv.
  3. Les workflows GitHub Actions qui déploient sur label.
