# 0032 Mobile builds and releases

Status: accepted; store decisions (TestFlight only, no store submission, iOS in the release run) superseded by 0039

## Context
The Tauri app gets Android and iOS targets (in-process SSH transport, mobile UI). They need a
build on pull requests, and a way to reach the team's phones on every release, within the
pipeline of ADR 0027: Linux jobs on `ubuntu-24.04` (JDK 21 from `actions/setup-java`, the
image's Android SDK with platform 36 and its default NDK), Apple builds on GitHub-hosted
`macos-26`, one release run per push to `main`.

fastlane match (certificates in a private Git repository, App Store Connect API key secrets) is
the usual way to sign iOS builds in CI on `macos-26`.

## Decision
- **Generated projects are committed**: `app/src-tauri/gen/android` and `gen/apple`, generated by
  `pnpm tauri {android,ios} init --ci` in CI (`mobile-init.yml`, manual) because nothing heavy
  runs on developer machines. Only `gen/schemas` stays ignored. Committing them lets the release
  signing config and SDK levels live in the Gradle file and keeps builds reproducible.
- **Identifier** `io.github.basilelt.overseer` for both, the desktop one; it suits both stores.
  No development team is committed: the iOS release job writes the `APPLE_TEAM_ID` secret into
  the Xcode project and passes it as `APPLE_DEVELOPMENT_TEAM` to Tauri. Both platform configs
  empty `bundle.resources`: phones carry no daemon binaries.
- **Android: APK on the GitHub Release, no Play Store.** One universal release APK
  (arm64-v8a + armeabi-v7a), `Overseer_<version>_android.apk` with a `.sha256`, installed and
  updated with Obtainium (GitHub source, APK regex) or by hand. One
  file is what Obtainium and `gh release download` handle without per-ABI filters; x86/x86_64
  would add release builds for emulators only. Signed with a dedicated release keystore given as
  secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
  `ANDROID_KEY_PASSWORD`); Gradle reads them from the environment only when
  `ANDROID_KEYSTORE_PATH` is set, so debug builds are unaffected. `apksigner` checks the signature
  and, when the `ANDROID_CERT_SHA256` variable is set, the pinned certificate fingerprint before
  upload. Compile SDK and target SDK 36.
- **iOS: TestFlight only.** fastlane lane `internal_testflight` (`app/fastlane`): temporary
  keychain, App Store Connect API key, `match(type: "appstore", readonly: true)` from
  `MATCH_GIT_URL` over SSH with `MATCH_SSH_PRIVATE_KEY`. Tauri signs iOS builds from `IOS_CERTIFICATE` and
  `IOS_MOBILE_PROVISION`, so the lane exports the matched identity to a `.p12` and lets
  `pnpm tauri ios build --export-method app-store-connect` build and sign; `build_app` on the
  generated Xcode project would bypass Tauri's build of the Rust library. Upload with
  `upload_to_testflight(skip_submission: true, skip_waiting_for_build_processing: true)`: the
  macOS runner is freed, internal testers get the build through the group's automatic
  distribution. `CFBundleVersion` is the run number (`<run>.<attempt>` on re-runs),
  `CFBundleShortVersionString` the release version; the lane checks both in the IPA.
- **No store submission, enforced**: `scripts/store-guard.sh` fails CI and the iOS job on
  `deliver`, `upload_to_app_store`, `submit_for_review`, `submit_beta_review`,
  `distribute_external`, `supply`, `upload_to_play_store`, and on a TestFlight upload without
  `skip_submission: true`.
- **Releases never break on mobile**: the `tag` job checks the mobile secrets; a job whose secrets
  are missing is skipped with a warning. `publish` waits for `app-android` but does not require
  it; `app-ios` is `continue-on-error` and not a dependency of `publish` (it adds no asset).
- **Pull requests**: a debug APK build for arm64 on `ubuntu-24.04`, uploaded as an artifact. No iOS
  build on pull requests (macOS minutes; the iOS lane runs on release).

## Consequences
- `ci.yml` gates releases, so its `android` job requires the app crate to build for Android
  (mobile entry point, desktop-only plugins behind `cfg(desktop)`).
- Regenerating with `mobile-init.yml` (force) overwrites the Gradle signing block and SDK levels;
  re-apply them (docs/mobile.md).
- The Android release key cannot change without users reinstalling the app.
- One-time human steps for iOS (bundle id, App Store Connect record, TestFlight group, match
  profile, export compliance, secrets) are in `docs/mobile.md`.
- Two release builds of the Rust crate per release on Linux for Android, one on macOS for iOS.

## Addendum: in-app updates on Android

`tauri-plugin-updater` does not support Android, and Obtainium is one more app to set up. The
Android build now updates itself from the same release assets
(`Overseer_<version>_android.apk` + `.sha256`).

- **Check**: `GET /repos/basilelt/overseer/releases/latest`;
  semver of the tag against the installed version; the asset ending in `_android.apk` and the
  asset named `<apk>.sha256` must both be present, else there is nothing to install. Checked at
  start, every 6 h, on resume (at most every 15 min) and by hand.
- **Token**: written when the repository was private, the app asked once for a GitHub token and
  stored it with the device key's `Secrets` (Android Keystore-backed
  `android-native-keyring-store`), never returned to the web view. The repository is now public:
  release reads need no token, and a saved one only lifts the anonymous API rate limit.
- **Download**: the asset's API URL with `Accept: application/octet-stream` (and
  `Authorization: Bearer` when a token is saved), redirects disabled; the signed storage URL from `Location`
  is fetched by a second request without the `Authorization` header. TLS uses the bundled
  `webpki-root-certs`: reqwest's platform verifier needs a JNI initialisation that the app does
  not do. The APK is streamed to `<cache>/updates/`, hashed while it is written, compared with the
  `.sha256`, and only then renamed from `.part`; earlier downloads are deleted first.
- **Install: `ACTION_VIEW` on a `FileProvider` URI**, not a `PackageInstaller` session. One intent,
  the system installer does the confirmation, and there is no session, broadcast receiver or
  status callback to keep alive while the app is replaced. What a session would add is the
  failure status; the one failure users can cause (a debug build from a pull request installed,
  signed with another key) is detected before the intent: the plugin compares the signing
  certificates of the downloaded archive and of the installed package, and the app explains to
  uninstall once. `REQUEST_INSTALL_PACKAGES` is declared; when
  `canRequestPackageInstalls()` is false the app explains, then opens
  `ACTION_MANAGE_UNKNOWN_APP_SOURCES` for its package, and retries when it comes back.
- **Plugin**: `ApkInstallerPlugin.kt` lives in the generated Android project
  (`gen/android/app/src/main/java/io/github/basilelt/overseer/`) and is registered by an Android-only
  inline Tauri plugin (`apk_update::installer_plugin`). The app module already depends on
  `:tauri-android` and already declares a `FileProvider` (`${applicationId}.fileprovider`, cache
  path `.`), so no Gradle module or extra crate is needed and the `android` CI job compiles it.
  The Kotlin file and the permission are hand edits to re-apply after a forced regeneration
  (docs/mobile.md).
- **iOS** stays on TestFlight; the updater is not shown there.

## Addendum: Google Play

Superseded in part by 0039: the App Bundle is no longer built or uploaded by `release.yml`; the
manual `store.yml` builds it with `OVERSEER_DISTRIBUTION=play`, runs the same checks and uploads it
to the track chosen at dispatch, production included. `scripts/android-play-track.sh` and the
`PLAY_TRACK`/`PLAY_RELEASE_STATUS` variables are gone. Play App Signing ended up with a key
generated by Google, so the Play build and the GitHub APK do not share a signing certificate.
The build-time removal of the updater and the 16 KB checks below still hold.

The "no Play Store" decision is narrowed: the GitHub Release APK stays the main Android
channel, and each release also uploads an App Bundle to a Google Play **testing** track. Production
on Play stays out of CI.

- **Two artifacts from one job.** `app-android` builds the APK as before, then a signed AAB
  (`--aab --target aarch64 --target armv7`) with the same release keystore. The user registers that
  key with Play App Signing and uses it as the upload key, so the GitHub APK and the Play build
  share one signing certificate. The AAB is the `play-android` artifact, not an `app-*` one, so it
  is never attached to the GitHub Release.
- **No self-update on Play, removed at build time.** Play policy forbids an app it distributes
  from installing updates itself, so the Play build does not contain the in-app updater at all;
  hiding it at run time is not enough. One switch, `OVERSEER_DISTRIBUTION=play`, set only on the
  AAB step, drives every layer:
  - Rust: `build.rs` sets the `self_update` cfg unless the distribution is `play` or the target
    is iOS (`src/distribution.rs`, shared with the build script and unit-tested). `apk_update`
    (the release check, download, checksum, installer plugin and its five commands) is compiled
    only under `self_update`; the HTTP helpers the server download to a host also uses live in
    `release_http`, which every build keeps.
  - Kotlin: `ApkInstallerPlugin.kt` lives in `app/src/selfupdate/java`, a source directory Gradle
    adds only when the distribution is not `play`. The Play build's `release` manifest is
    `app/src/play/AndroidManifest.xml`, which removes `REQUEST_INSTALL_PACKAGES` and the
    installer's `FileProvider` through the manifest merger (`tools:node="remove"`).
  - Web view: `vite.config.ts` defines `__SELF_UPDATE__` from the same variable and from
    `TAURI_ENV_PLATFORM` (false for `play` and for iOS). Every entry point (update pill, Settings
    row, More row, command palette, the updater start and its sheet) is behind that constant, so
    the bundler drops `apk-update.svelte.ts` and the `ApkUpdate*` components from those builds.
    `app/src/lib/perf/bundle.test.ts` builds the Play and iOS bundles and checks that no updater
    module or command name is left.
  - Checks on the artifacts: `scripts/android-aab.sh` fails if the AAB declares
    `REQUEST_INSTALL_PACKAGES` or the `FileProvider`, or if its dex contains
    `ApkInstallerPlugin`; `scripts/android-apk.sh` fails if the GitHub APK lacks either.

  iOS never used the updater (`apk_update_status` reported it unsupported); it is now left out of
  the iOS build the same way. A Cargo feature or a Gradle product flavor was the alternative.
  Tauri already uses the `abi` flavor dimension and finds its outputs by path, and the Tauri CLI
  would need a feature flag on one of two builds; an environment variable read by `build.rs`,
  Gradle and Vite keeps the output paths and gives the three layers one source of truth.
- **16 KB pages.** Play requires 16 KB aligned native libraries for apps targeting Android 15+.
  Both Android jobs build with the newest NDK on the runner (`ANDROID_NDK_LATEST_HOME`, r28 or
  later, whose linker aligns to 16 KB by default), and `scripts/android-16k.sh` checks every
  64-bit library's `LOAD` segments (and the APK's zip alignment with `zipalign -c -P 16`). The
  release APK and the pull-request debug APK are checked too.
- **Upload**: `app-android-play` (needs `app-android`, not a dependency of `publish`) uploads with
  `r0adkll/upload-google-play`, pinned by commit, when the `PLAY_SERVICE_ACCOUNT_JSON` secret is
  set; otherwise the `tag` job warns and the job is skipped. Track and status come from the
  `PLAY_TRACK` (default `internal`) and `PLAY_RELEASE_STATUS` (default `completed`, or `draft`)
  repository variables, checked by `scripts/android-play-track.sh`, which rejects `production`.
  An upload failure marks that job red and never blocks the GitHub Release.
- **Guard**: `scripts/store-guard.sh` still fails on App Store submission and on fastlane
  `supply`/`upload_to_play_store`; it now also fails on a Play production track anywhere, on a
  staged rollout (`userFraction`), and on a Play upload whose track does not come from
  `scripts/android-play-track.sh`. `scripts/store-guard.test.sh` pins each case.
- **Consequences**: one more release build of the Rust crate per release (the AAB step changes
  the build environment, so the app crate recompiles); the first AAB must be uploaded by hand in
  the Play Console before the API accepts uploads; promotion to production is a manual step in
  the Play Console.
